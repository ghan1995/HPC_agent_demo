# HPC Agent 产品决策记录

本文件记录已经形成共识、会影响后续产品与交互设计的重要决策。它不代替需求文档；当结论发生变化时，应保留原决定及变更原因。

## D-001 统一从多瑙顶部栏进入

- 日期：2026-09-18
- 状态：初步确认
- 决策：HPC Agent 初期以多瑙平台顶部栏中的智能体图标作为统一入口。点击后进入独立的浏览器网页，不使用桌面客户端。
- 原因：为查询、诊断、计划、工具过程和操作确认提供完整空间，同时保持入口统一。
- 后续关注：独立网页与原多瑙页面之间的返回路径、状态保持和对象跳转方式。

## D-002 预留来源任务和当前对象上下文区

- 日期：2026-09-18
- 状态：方向确认，细节待验证
- 决策：用户从特定任务或对象页面进入智能体时，对话区域需要预留一个可展示来源上下文的区域。初期重点支持当前作业信息，后续可扩展到集群、节点、队列和告警等对象。
- 可能展示的信息：
  - 当前集群；
  - 当前作业或其他对象；
  - 来源页面或来源任务；
  - 数据更新时间；
  - 用户可执行的查看、切换或清除上下文操作。
- 设计原则：上下文必须对用户可见，不能在后台静默继承后直接影响判断或执行。
- 后续关注：
  - 顶部栏全局入口能否可靠获得当前页面上下文；
  - 哪些筛选条件和临时页面状态需要继承；
  - 上下文过期、对象无权限或对象已不存在时如何表达；
  - 一个任务涉及多个作业时，上下文区如何扩展。

## D-003 用户只面对一个统一智能体入口

- 日期：2026-09-18
- 状态：初步确认
- 决策：不同任务可以由不同专业子 Agent 执行，但不要求用户人工选择或切换 Agent。用户始终从统一对话区域描述目标，由系统识别任务、拆分工作并调度合适的子 Agent。
- 原因：用户的目标是完成集群查询、作业操作或异常诊断，不应先理解系统内部的 Agent 分类和组织方式。
- 设计原则：
  - 面向用户强化任务和结果，不强化 Agent 名称和组织结构；
  - 子 Agent 的存在只在有助于理解进度、责任、等待或失败原因时出现；
  - 不把“选择 Agent”作为任务开始前的必经步骤；
  - 需要用户补充信息时，以任务问题进行询问，而不是要求用户改选另一个 Agent。

## D-004 子 Agent 状态在对话区分层展示

- 日期：2026-09-18
- 状态：方向确认，信息层级待验证
- 决策：统一对话区可以折叠展示各子 Agent 的工作状态，并支持按需查看详细过程。
- 默认层级建议：
  1. 默认只显示面向任务的总体状态，例如“正在收集作业信息”“正在分析失败原因”“等待确认”；
  2. 展开后显示子任务、所用工具、当前状态、等待原因、阶段结果和异常；
  3. 只有在诊断、审计或失败恢复需要时，才进一步显示某个子 Agent 的详细记录。
- 展示位置补充：子 Agent 的当前阶段、主要状态和阶段结果直接出现在对话区的任务过程块中，并支持折叠展开；右侧检查器用于查看更完整的路由、协作消息、工具事件和历史日志，不代替对话区的状态展示。
- 不建议默认暴露：
  - 内部路由判断；
  - 无助于用户决策的 Agent 名称；
  - 内部提示词；
  - 模型的私有思维过程；
  - 高频、低价值的 Agent 间通信。
- 补充：以上信息不作为默认主视图内容，但可以通过展开区域或侧边检查器按需查看，包括子 Agent 名称、协作消息、路由结果和更详细的运行日志。内部提示词、密钥及模型私有思维过程仍不对用户展示。
- 需要保留：
  - 使用了什么系统数据和工具；
  - 当前步骤及等待原因；
  - 哪些结果是事实、推断或建议；
  - 哪个子任务失败以及对总体结果的影响；
  - 涉及写操作时的权限、影响范围和确认状态。

## D-005 工作台采用三类区域职责

- 日期：2026-09-18
- 状态：方向确认，布局细节待验证
- 决策：智能体工作台初步采用左侧会话区、中间对话与任务区、右侧检查器三类区域。它们是职责划分，不代表所有功能都需要独立常驻面板。
- 左侧会话区：
  - 新建对话；
  - Session 列表和管理；
  - 根据运行状态进行分类或筛选；
  - 突出等待人工确认、运行中、异常和已完成的 Session。
- 中间主工作区：
  - 用户与统一智能体的对话；
  - 任务计划、任务状态和人工确认；
  - 文档、报告等产物的生成状态和入口；
  - 对话输入及附件、审查等级等控制。
- 右侧检查器：
  - 查看文档类产物；
  - 查看从多瑙特定任务或对象继承的上下文；
  - 查看整体智能体及子 Agent 的运行日志和协作详情；
  - 根据用户当前选择的对象、产物或任务切换内容。

## D-006 Session 需要面向任务状态进行管理

- 日期：2026-09-18
- 状态：方向确认，状态模型待定义
- 决策：Session 不只是聊天历史。由于存在并行任务、长时间运行和人工确认，左侧列表需要支持按运行状态分类、筛选或聚合。
- 初步需要区分：
  - 运行中；
  - 等待用户确认；
  - 等待用户补充信息；
  - 异常或部分失败；
  - 已完成；
  - 已中断或已取消。
- 后续关注：一个 Session 是否允许同时包含多个独立任务，以及列表的主状态由哪个任务决定。

## D-007 输入区保留扩展位但不引入运行平台选择

- 日期：2026-09-18
- 状态：初步确认
- 决策：输入区当前保留附件和执行审查等级，并为未来的 Skill、模型或其他能力选择预留扩展位置，但初期不要求实现。由于系统直接连接固定后台，不提供运行平台选择。
- 说明：从多瑙特定任务进入时继承的作业或对象属于“任务上下文”，不是运行平台。它应在上下文区展示，并可以被用户查看、切换或清除，不应与输入区的平台选择控件合并。

## D-009 审查等级表示执行前的人工审批强度

- 日期：2026-09-18
- 状态：定义确认，等级方案待验证
- 决策：“审查等级”用于控制智能体执行操作前的人工审批强度，不表示回答质量、推理深度或模型能力。
- 推荐名称：界面中优先使用“执行审查”或“审批策略”，减少与内容审查、结果复核的混淆。
- 核心约束：
  - 系统根据操作风险、用户权限和组织策略确定最低审批要求；
  - 用户可以主动提高审批强度，但不能低于系统规定的最低等级；
  - 查询、分析和生成建议通常不需要执行审批；
  - 写操作需要展示目标对象、参数差异、影响范围和可恢复性；
  - 高风险或批量操作必须逐项或按明确范围确认；
  - 用户在 Session 中选择的等级不能覆盖取消作业、节点维护等操作的强制确认规则；
  - 审批记录需要进入任务历史和运行日志。
- 初步等级方向：
  - 自动：低风险、策略允许的操作可以自动执行；
  - 关键步骤确认：只在写操作或重要分支前确认；
  - 每步确认：每个可产生外部影响的步骤都需要确认。
- 后续关注：是否允许按 Session 设置默认等级，以及任务执行过程中风险升高时如何自动升级审批要求。

## D-010 Task 需要固定入口和集中查看区

- 日期：2026-09-18
- 状态：方向确认，具体位置待原型验证
- 决策：Task 不只作为对话消息中的过程对象存在。中间主工作区需要一个始终可找到的 Task 入口，用于集中查看当前 Session 内的运行中、等待确认、异常和已完成任务。
- 推荐结构：
  - 对话流中的任务过程块：负责展示任务创建、阶段更新、人工确认和结果；
  - 固定 Task 入口：负责随时返回任务列表，不受对话滚动位置影响；
  - Task 集中查看区：展示任务列表、状态、进度、关联对象和操作；
  - 右侧任务详情：用户选中某个任务后查看步骤、子 Agent、工具和运行日志。
- 入口位置候选：
  - 输入框上方的任务状态条：更适合持续提示当前运行任务、等待确认和异常；
  - 对话顶部固定入口：更适合查看当前 Session 的全部任务；
  - 两者可以组合，但不应重复展示完整内容。
- 初步建议：对话顶部保留“任务”集中入口；输入框上方只显示需要持续关注的当前任务状态和待确认提示。点击两处入口均可进入同一个 Task 集中查看区。

## D-011 提供贯穿任务前后的问题引导

- 日期：2026-09-18
- 状态：方向确认，推荐规则待验证
- 决策：新对话首页提供推荐案例；每个阶段性回答或任务结束后提供与当前上下文相关的下一步问题或操作建议。
- 新对话首页推荐内容：
  - 覆盖集群查询、作业管理与提交、作业异常诊断三类核心场景；
  - 根据当前用户角色、权限和从多瑙继承的页面上下文进行调整；
  - 推荐项使用用户任务语言，不以 Skill 或子 Agent 名称组织；
  - 推荐案例应能直接发起，也允许用户修改后再发送。
- 对话后的下一步建议：
  - 与当前结论、未完成事项和用户权限相关；
  - 区分“继续提问”“查看证据”“创建新任务”和“执行操作”；
  - 涉及写操作的建议不能因被推荐而绕过审批；
  - 当证据不足时优先建议补充信息或继续检查，不能直接推荐高风险动作；
  - 已完成任务应推荐验证结果、查看产物或处理相关对象，而不是重复相同问题。

## D-012 区分回答重试、任务重跑和业务再执行

- 日期：2026-09-18
- 状态：方向确认，具体操作规则待定义
- 决策：提供常规 Agent 的重试、编辑后重发等能力，但不能用一个含糊的“重新跑”按钮同时表示重新生成回答、重新执行任务和重新执行 HPC 写操作。
- 需要区分：
  - 重新生成回答：基于已有事实重新组织或解释，不重新调用业务工具；
  - 重新分析：重新运行查询、诊断或检查，可能使用更新后的数据；
  - 从失败步骤重试：保留已完成步骤，只重试失败或中断的步骤；
  - 重新执行操作：再次提交、取消、修改等，会产生新的外部影响；
  - 重新提交作业：创建新作业，必须显示参数、目标和影响，并遵守审批策略。
- 核心约束：
  - 所有重试都要说明将复用哪些数据、重新获取哪些数据；
  - 对非幂等写操作不得静默重放；
  - 重新执行前应检查目标对象当前状态，避免重复提交或重复取消；
  - 新一次运行应产生独立 Run 记录，并与原 Run 建立关联；
  - 用户应能看出结果来自原数据还是最新数据。

## D-013 保留常规对话操作能力

- 日期：2026-09-18
- 状态：方向确认
- 决策：在不削弱任务安全性的前提下，保留常规 Agent 对话体验，包括编辑后重发、复制、反馈、停止生成、继续生成和重新生成回答。
- 后续关注：编辑历史消息后是覆盖原分支还是创建新分支，以及原 Task、Run 和 Artifact 如何保留与标记。

## D-014 独立 Agent 页面采用简洁开放式布局

- 日期：2026-09-18
- 状态：方向确认
- 决策：独立 Agent 网页不复制多瑙门户顶栏，也不使用大量后台面板或卡片包裹对话。整体参考当前主流 Agent 产品和既有 AI Elements 组件的简洁表达。
- 视觉与布局原则：
  - 页面无多瑙顶部导航栏；
  - 中央对话区使用开放画布，不增加完整外框或大卡片容器；
  - 助手回复默认不使用聊天气泡，以连续内容块呈现；
  - 用户输入可以保留弱背景或轻量边界，以区分消息方向；
  - 推荐案例使用简洁文本入口或轻量列表，不使用大面积卡片矩阵；
  - 输入框是页面主要固定控件，可使用轻微边框或阴影，但避免多层嵌套；
  - 主操作按钮暂时使用黑色，蓝色只用于链接、选中或系统语义；
  - 左侧 Session 区保持轻量列表；右侧检查器默认关闭，按需打开；
  - Task、产物、运行日志和子 Agent 详情按任务需要出现，不在空白首页同时铺开。

## D-015 默认首页的基础交互结构

- 日期：2026-09-18
- 状态：部分被 D-020 修订；其余内容已进入前端原型
- 决策：
  - 输入框固定在主工作区底部；
  - 左侧 Session 只按“需要处理”和“最近”做轻量分组；
  - 每条 Session 自身显示待确认、运行中、已完成或已中断等运行状态；
  - Session 搜索默认收起为图标，点击后打开左侧浮层并即时筛选；
  - 空白首页只展示推荐案例、输入区和必要的任务入口，不展示右侧检查器和完整任务过程。

## D-008 右侧区域作为可切换检查器复用

- 日期：2026-09-18
- 状态：方向确认
- 决策：右侧不为文档、上下文、子 Agent 和运行日志分别建立多个常驻面板，而是使用一个可切换、可关闭的检查器承载详细内容。
- 可能的查看模式：
  - 上下文；
  - 产物；
  - 任务详情；
  - 运行日志；
  - 子 Agent 协作详情。
- 触发方式：用户从中间对话、任务卡、产物入口或专门的运行日志入口打开对应内容；检查器标题和内容随当前选择切换。

## D-016 历史对话完成态的基础结构

- 日期：2026-09-20
- 状态：已形成基础 HTML 原型，待体验评审
- 决策：
  - 对话标题栏横贯主工作区并与正文形成明确分隔；从业务对象进入时，将当前集群、当前对象、来源和数据更新时间作为标题栏下的可选上下文层展示，支持收起；普通入口未继承对象时不出现该层；
  - 工作过程采用两级渐进披露：整体默认折叠；展开整体后仅显示步骤标题，各步骤的说明、证据和参考资料仍默认隐藏，由用户单独展开查看；
  - Task 入口以略窄于输入框、无外边框的任务托盘固定在输入框上方，并与输入框连接成整体；收起时优先展示当前步骤、总体状态和步骤统计；点击后由同一托盘的上沿向上增高并展开任务详情，不弹出独立浮层；展开态不重复保留底部摘要行，改由任务步骤标题行承担收起入口；回复内同时提供任务摘要入口，并打开同一个任务托盘；
  - 子 Agent 协作状态在回复中默认折叠，只展示专业角色、完成状态和可审计的工作摘要，不展示私有思维过程；
  - 文档产物以回复内对象行呈现，点击后复用右侧检查器查看；
  - 运行日志从对话顶部进入右侧检查器，仅展示工具调用与状态事件；
  - 右侧检查器属于主工作区布局，打开时压缩对话区，不以浮层覆盖对话内容；
  - Session 列表收起后完全退出布局，不保留窄侧栏；重新展开入口在对话页放在标题旁边，在首页固定于左上角；
  - 回复结束保留复制、反馈和重新分析，并提供与当前结论相关的下一步建议；
  - “重新分析”与会产生外部影响的“重新提交作业”分开表达，后者仍需确认参数和审批；
  - 右侧检查器默认关闭，避免历史对话首次打开时形成三栏拥挤界面。

## D-017 建立统一的视觉层级基线

- 日期：2026-09-20
- 状态：方向确认，随原型持续校准
- 决策：后续页面和组件优化必须先服从统一的信息层级，再处理局部装饰。能参考 AI Elements 等成熟组件时，优先沿用其结构、交互和默认视觉逻辑，只做符合 HPC 业务语义的克制适配，不自行创造缺少依据的组件样式。
- 视觉层级原则：
  - 文字按“主标题 / 正文 / 次级说明 / 元信息与状态”逐级降低字号、字重和颜色对比度；同一语义层级在不同组件中保持一致；
  - 当前基础文字色阶为 `#171717`（强信息）、`#333333`（正文）、`#666666`（次级信息）、`#999999`（说明与元信息）、`#B8B8B8`（禁用）；
  - 页面默认使用白色开放画布。浅灰底色只用于确有分组、状态或可操作语义的区域，不能把每个内容块都做成卡片；
  - 分隔优先依靠留白、字号、字重和颜色；只有相邻内容仍难以辨认时才增加弱分隔线，避免同时叠加底色、边框和阴影；
  - 工作过程属于辅助过程信息，整体应比最终答复降低一个视觉层级：默认透明背景，以较弱文字色、较小字号和时间线表达，不与正文争夺注意力；
  - Task 属于用户可操作的执行对象，层级高于工作过程；子 Agent 属于可审计的协作详情，默认弱化并折叠；三者不应使用相同的视觉重量；
  - 交付前必须同时审视整页的信息层级、组件间区分、对齐、密度与美观度，并验证展开、收起、悬浮和焦点等状态，而不只验证功能是否可用。

## D-018 Task 计划只由底部托盘承载

- 日期：2026-09-21
- 状态：方向确认
- 决策：对话正文不再重复展示 Task 计划组件；“工作过程”和“子 Agent 协作”仍属于每轮回复的可审计过程信息，Task 计划则只在输入框上方的底部托盘展示。
- 轮次规则：托盘始终对应当前最新对话轮次。用户发起新一轮请求后，托盘直接替换为该轮的新计划并恢复收起态，不并列堆放或继续展示上一轮计划。
- 高度规则：展开托盘保持紧凑最大高度；任务超出可用空间时仅在托盘内部滚动，避免持续向上遮挡或挤压对话内容。

## D-020 工作过程与 Subagent 协作采用并列投影

- 日期：2026-09-22
- 状态：已实现，待持续验证
- 决策：“工作过程”与“Subagent 协作”是同一次运行的两个一级并列视图，不再将完整 Subagent 详情固定嵌套在某个工作步骤中。
- 关系：工作过程按任务阶段组织，Subagent 协作按执行者组织；两者读取同一份运行状态，通过轻量引用双向关联。
- 展开策略：完成态默认均收起；新运行默认展开工作过程、收起 Subagent；等待或失败来自 Subagent 时，自动提升相关协作详情的可见性。
- 边界：界面展示可审计的阶段、工具、依据和 Agent 输入输出，不展示模型私有原始思维链。
- 视觉约束：
  - 中性表面、文字、边框、输入和侧栏颜色统一使用语义 Token；
  - 蓝、绿、琥珀和红分别用于运行、完成、等待和失败；
  - 视觉层级优先通过留白、字号、字重、底色和 1px 边框建立，阴影仅用于需要明确浮层或操作层级的区域；
  - 普通图标使用 SVG 并继承 `currentColor`，不用无语义色块包裹；
  - 输入区不能因为局部提交按钮禁用而整体表现为不可用。

## D-021 工作过程与 Agent 协作统一归入思考过程

- 日期：2026-09-23
- 状态：已实现；修订 D-020 的一级信息架构，保留其共享状态与双向关联原则
- 决策：“思考过程”是正式结论之前唯一的一级过程容器。“工作过程”按任务阶段组织，“Agent 协作”按执行者组织，二者作为容器内的并列投影视图，不再与最终结论竞争一级视觉层级。
- 折叠策略：运行时默认展开；完整结论输出后自动折叠为“已思考时长、活动数、Agent 数量”的单行摘要。等待确认、失败或结论冲突时保持展开；用户手动改变披露状态后，后续普通流式更新不抢夺控制。
- 交互边界：操作确认卡与最终结论位于思考过程之外，不因过程折叠而隐藏。界面展示的是可审计的阶段、工具、证据和 Agent 输入输出，不是模型私有原始思维链。

## D-020 Session 列表采用待处理置顶和项目分组

- 日期：2026-09-21
- 状态：已实现
- 修订：替代 D-015 中“需要处理”和“最近”的分组方式。
- 决策：需要用户处理的 Session 独立置顶；其余 Session 按所属项目分组。每条 Session 仅保留单行状态和标题，项目、更新时间等元信息在悬浮卡中展示，悬浮时在行尾提供更多操作。
- 原因：项目分组更符合 HPC 工作围绕集群、作业和项目持续推进的使用方式，同时避免在高频列表中重复展示低优先级元信息。

## 当前待讨论问题

1. 用户是否需要知道子 Agent 的专业角色名称，还是始终只看到任务步骤？
2. 一个子 Agent 失败时，主 Agent 应自动换方案、降级完成，还是先提示用户？
3. 多个子 Agent 并行工作时，总体进度如何表达，避免产生虚假的百分比？
4. 子 Agent 产生冲突结论时，由谁仲裁，如何向用户表达不确定性？
5. 对话历史按会话保存，还是按可恢复、可追溯的任务保存？
6. 从特定作业进入后，新话题是否继续默认绑定该作业？
