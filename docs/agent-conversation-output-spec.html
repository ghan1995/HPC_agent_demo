HPC Agent 对话流输出规范

为作业提交、故障处理、资源申请、环境配置和通用咨询建立统一、可预测的回答骨架。结构保持一致，内容按任务复杂度和风险动态增减。

适用对象：HPC Agent 产品与交互设计原则：先确认，再计划，再执行，最后闭环

1. 规范目标

统一的是信息顺序与表达责任，不是强迫所有任务输出相同长度。简单咨询可以压缩为三段，执行型任务则完整展示过程、状态和结果。

1可预期

用户在不同主题下都能快速找到需求理解、方案、执行结果和下一步。

2可审计

关键输入、操作、证据和结果有明确来源；展示可审计过程，而不是模型私有思维链。

3可行动

每轮输出都明确当前状态、是否需要确认，以及用户接下来能做什么。

ⓘ
“思考”在界面中的正确含义展示经过整理的任务理解、判断依据和执行计划；不展示模型逐字推理、内部草稿或不可验证的思维过程。

2. 标准对话流

七个阶段描述 Agent 的工作逻辑，不代表七段内容都要永久留在对话里。理解、规划和执行过程进入“思考中”，任务完成后折叠；结果、风险、产物和下一步进入“最终呈现”，始终可见。需要用户操作的交互卡片独立于两者，在等待期间保持可见。

可折叠 · 工作过程理解需求、参数检查、方案规划、执行进度、工具调用、Subagent 协作和过程证据。完成后收起为耗时与阶段摘要。
始终可见 · 最终呈现结果结论、关键证据、风险、生成产物和后续操作。用户无需重新展开过程即可获得完整答案。
1理解需求识别目标与缺口
2需求摘要确认范围与约束
3方案与计划说明步骤和判断点
4执行过程展示进度与证据
5结果结论回答是否完成
6风险提示说明影响与限制
7后续建议提供下一步入口

3. 必选与可选矩阵

需要区分两类结构：七阶段是回答内容的主流程；参考资料、工具、确认、产物等是按任务触发的横切组件。主流程保持顺序稳定，横切组件插入对应阶段。

4. 各阶段内容责任

每一阶段只承担一种主要责任。第 1–4 阶段属于可折叠的工作过程；第 5–7 阶段属于始终可见的最终呈现。

1

理解需求

识别意图与信息缺口

  • 判断任务主题与用户目标
  • 区分事实、假设与待确认项
  • 必要时只询问会改变方案的关键问题
“我理解你要在 GPU 集群上提交一个训练作业，并确认资源参数是否合理。”
2

需求摘要

让双方确认同一件事

  • 提炼目标、对象和成功标准
  • 列出已知参数与约束
  • 标注缺失信息，不重复用户原话
“目标：提交训练任务；资源：4 × A100；入口脚本：train.py；队列：gpu。”
3

方案与计划

说明准备怎么做

  • 给出可执行的步骤与顺序
  • 标注需要确认或可能分支的节点
  • 复杂任务给出计划，简单任务可压缩成一句
“先检查参数与队列约束，再生成脚本，确认后提交，最后回传作业 ID。”
4

执行过程

展示进度、证据与操作

  • 仅展示有用户价值的阶段进度
  • 工具调用、Subagent 和证据按需展开
  • 状态使用文字与图标共同表达
“✓ 参数检查通过　● 正在生成脚本　○ 等待提交确认”
5

结果结论

直接回答是否完成

  • 首句给出结论，不让用户自行归纳
  • 提供结果标识、关键证据或失败原因
  • 失败也必须形成明确结论
“作业已成功提交，作业 ID 为 123456，当前状态为 PENDING。”
6

风险提示

说明影响、边界与不确定性

  • 解释风险发生条件与影响范围
  • 给出规避或恢复方式
  • 不能确认时明确说明证据不足
“当前队列较拥塞，预计等待约 2 小时；该时间基于当前快照，可能变化。”
7

后续建议

提供自然的下一步

  • 优先提供一到两个最相关操作
  • 使用具体动作，不使用泛泛的“还有问题吗”
  • 必要时附查看位置或命令
“接下来可以持续查看排队状态，或在等待过长时切换到 gpu-short 队列。”

6. 状态与渐进披露规则

状态必须同时依靠文字、图标和位置表达；颜色只作为辅助。信息量随任务复杂度增加，但首屏始终保留结论性信息。

已完成

操作成功或阶段结束。必须给出结果，不只写“完成”。

进行中

说明当前正在做什么，避免持续刷出低价值日志。

等待 / 风险

说明等待对象、用户是否需要行动以及潜在影响。

失败

说明失败点、已完成部分、影响范围和可恢复路径。

任务结束后始终可见

  1. 结果结论和完成状态
  2. 支撑结论的关键证据
  3. 风险、限制及恢复方式
  4. 产物入口和后续操作

任务结束后默认折叠

  1. 任务理解、信息缺口和方案计划
  2. 执行进度、工具调用与原始输出
  3. Subagent 分工和详细运行记录
  4. 过程日志、临时配置及中间产物

6.1 人工交互作为运行中断点

需要用户输入或授权时，使用独立交互卡片暂停流程，而不是预设一条用户自然语言回复。卡片必须提升到“思考中”容器之外，避免在过程收起后被隐藏；后续工具和 Subagent 暂停执行。

参数补充卡片

  1. 用于选择时限、队列、资源规格等缺失参数
  2. 提供推荐值、常用选项和自定义入口
  3. 操作结果记录为“用户选择”，不伪造聊天回复

操作确认卡片

  1. 用于提交、删除、覆盖或产生资源消耗的动作
  2. 展示最终参数、影响范围和可恢复性
  3. 用户明确授权后才允许继续执行

!
确认卡片不能随过程自动收起成功完成后，确认卡片转为只读审计记录；等待确认或执行失败时，“思考中”保持展开。只有高风险、不可恢复或跨对象影响的操作才额外使用模态弹窗，对话中仍需保留确认记录。

7. 输出前检查清单

用于产品验收、提示词设计和 Agent 输出自检。并非所有模块都必须很长，但信息责任必须闭环。

“思考中”是否准确概括任务、缺口与计划，且没有机械复述用户原话？
需要推理的任务是否用“思考中”表达高层过程，并避免暴露私有原始思维链？
是否明确区分已知事实、假设和待确认信息？
执行前是否给出清晰方案和必要确认点？
高风险操作是否说明影响并获得用户确认？
执行过程是否只展示有决策价值的进度与证据？
工具、Subagent 与日志是否采用渐进披露？
外部事实和关键判断是否提供了就近的参考来源？
生成文件、脚本或报告时是否提供了清晰的产物入口？
结果首句是否直接回答“是否完成、结果是什么”？
失败时是否给出失败点、影响范围和恢复路径？
不确定结论是否标明依据和证据不足之处？
最后是否提供具体、有限且相关的下一步？
